## Motivation

[Cashu](https://cashu.space) ecash tokens can be stored on NFC chips, e.g. to give away ecash (tips, gifts). Payment requests allow to receive ecash. Both are defined in [Cashu NUTs](https://github.com/cashubtc/nuts) in text form with prefix and base64 encoding, which is not needed in machine-to-machine communication. To save space, CDF stores them as raw CBOR.

## General rules

- Payload of all minor types defined in this document is raw CBOR, without prefix and without base64 encoding.
- Labels as defined in [CDF-003](/CDF-003.md) MUST NOT be used.
- Version of Cashu serialization is given by minor type. New version MUST introduce a new minor type.

## Limitations

- Cashu token is bearer. Anyone who reads the record can claim the token, first claim wins.
- Reading a record does not remove it, so the token can be copied and claimed by somebody else before the intended recipient.
- Storage of tokens in NDEF records is not intended as a secure wallet.

## Minor types

| Mime type | Description             |
| :-------: | ----------------------- |
|  cdf/ct   | Cashu token V4          |
|  cdf/cr   | Cashu payment request A |

**cdf/ct**

- Cashu token V4 as defined in [NUT-00](https://github.com/cashubtc/nuts/blob/main/00.md)
- value MUST be CBOR serialized token V4 object
- equals to NUT-00 serialized token `cashuB<base64_token_cbor>` without `cashuB` prefix and base64 decoded
- equals to NUT-00 binary token `craw` `B` `<cbor>` without `crawB` prefix
- NDEF message MAY contain more `cdf/ct` records (e.g. tokens from different mints), order of records is not significant

**cdf/cr**

- Cashu payment request version A as defined in [NUT-18](https://github.com/cashubtc/nuts/blob/main/18.md)
- value MUST be CBOR serialized PaymentRequest object
- equals to NUT-18 serialized payment request `creqA<base64_cbor>` without `creqA` prefix and base64 decoded
- human readable description (e.g. "Savings", "My wallet") SHOULD be stored in PaymentRequest field `d`
