## Motivation

This data format supports various kinds of transactions - Lightning using LNURL and onchain with pub/priv keys. Multiple technologies in one memory unit requires clear differentiating between them. We introduce first minor types. 

### LNURL 

All lnurl records MUST be in `URI` format, not bech32 to save space in RFID chips. In machine-machine communication is no reason to use bech32 format at all. URL MUST use URL encoded `;` semicolon symbol if used.

With distinguished lnurlp and lnurlw records, one memory unit can be used to both receive and withdraw funds without LUD-19. 

### Labels

- Record MAY contain optional label, separated from value by semicolon delimiter `;` (`label;value`).
- Label MUST be UTF-8 encoded (plain ASCII is valid UTF-8).
- Reader MUST split payload at the first `;` only.

### Base URL

- Prefixed records (`cdf/lnpp`, `cdf/lnpw`) MUST be resolved against the last preceding `cdf/lnpb` record. Each new `cdf/lnpb` record replaces the previous one for all following records.
- Generator MUST place `cdf/lnpb` record before records which use it.
- Reader MUST ignore prefixed records without preceding `cdf/lnpb` record.
- Resulting URL is simple string concatenation of base and suffix (not RFC 3986 relative resolution).
- Generator SHOULD write base without trailing `/` and suffix with leading `/`.
- If base ends with `/` and suffix starts with `/`, reader MUST remove one of them. Reader MUST NOT insert `/` otherwise.

### Forward compatibility

- Reader MUST ignore unknown minor types.
- Incompatible changes MUST introduce a new minor type.

## Minor types


|   Mime type    | Description                                      |
| :------------: | ------------------------------------------------ |
|    cdf/lnp     | Pay url HIP-XX "Legacy"                          |
|    cdf/lnw     | Withdrawal url HIP-XX "Legacy"                   |
|    cdf/lnpb    | Base (prefix) URL                                |
|    cdf/lnpp    | Prefixed pay                                     |
|    cdf/lnpw    | Prefixed withdrawal                              |
|  cdf/k[coin]  | Private key for [coin] (cdf/kbitcoin - bitcoin) |
|  cdf/p[coin]   | Public address for [coin] (cdf/pbitcoin - bitcoin) |

**cdf/lnp**

- Pay url
- used to charge satoshis into RFID wallet
- Example: "Wallet1;https://mywallet.example.org/payurl?id=123"
- Example: "https://mywallet.example.org/payurl?id=123"

**cdf/lnw**

- Withdrawal url
- used to pay on POS/Vending machine etc by RFID
- rest same as lnurl/p

**cdf/lnpb**

- Base (prefix) URL
- Used to save space in other records
- Example: "https://mycoolnode.example.org/lnbitsinstance"
- Example result: "https://mycoolnode.example.org/lnbitsinstance" + "/lnpay?someid=123" = "https://mycoolnode.example.org/lnbitsinstance/lnpay?someid=123"

**cdf/lnpp**

- Prefixed Pay
- Pay URL suffix
- example: "Wallet 1;/lnpay?someid=123"

**cdf/lnpw**

- Prefixed Withdrawal
- Withdrawal URL suffix
- example: "Wallet 1;/lnwithdraw?someid=123"

**cdf/k[coin]**

- private key for [coin]
- [coin] MUST be full coin name in lowercase
- used as compatibility for POS or ATM for on-chain transactions on offline data storage (eg RFID tag)
- example: "cdf/kbitcoin" pKl..
- key in WIF format does not carry script type; historically, keys were used with legacy P2PKH (`1...`) addresses only
- reader SHOULD assume P2PKH and MAY also check other script types derived from the same key (P2SH-P2WPKH `3...`, P2WPKH `bc1q...`, P2TR `bc1p...`)
- *Open question: explicit script type signalling*

**cdf/p[coin]**

- public address for `[coin]`
- address type is detected by reader from address format (e.g. `1...`, `3...`, `bc1q...`, `bc1p...`)
- value MUST be address only, without URI scheme prefix (`bitcoin:`), coin is already given by MIME type
- example: "cdf/pbitcoin" 1PKabc..
- rest same as cdf/k`[coin]`
